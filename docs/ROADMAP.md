# 개발 로드맵과 배포 방식 검토

작성일: 2026-08-31
대상: `CBPrcsLab-HeatTransfer` 열전달 실험 교육용 웹 도구

이 문서는 기존 계획서(`260727_공실_열전달_학습툴_계획.md`)의 단계 구분을 유지하면서,
현재 코드의 상태를 반영하여 다음에 실제로 손대야 할 작업과 배포 방식을 정리한 것입니다.

## 1. 현재 상태 요약

단일 HTML 파일(2,129줄)에 마크업, 스타일, 스크립트가 모두 들어 있던 프로토타입을
다음과 같이 분리했습니다.

| 계층 | 위치 | 책임 |
|---|---|---|
| 마크업 | `index.html` | 화면 구조와 장치 SVG 도식 |
| 스타일 | `assets/css/` | 토큰·레이아웃·공통 컴포넌트·화면별 스타일 |
| 물리 모델 | `assets/js/physics/` | DOM에 접근하지 않는 순수 계산 함수 |
| 데이터 | `assets/js/data/` | 구성요소 설명, CFD case 메타데이터, 표 스키마 |
| 화면 | `assets/js/views/` | 입력값 읽기, 결과 표시, 그래프 그리기 |
| 공통 | `assets/js/core/` | DOM 유틸리티, 라우터, 캔버스 그래프, 수치 해석 |
| 검증 | `tests/`, `tools/` | 성질 테스트와 scipy 교차 검증 |

분리 과정에서 계산 결과가 달라지지 않았음을 확인했습니다. 원본 인라인 구현과 새 모듈의
출력을 실험 A 정상상태, 실험 B 센서 열수지, lumped model 시간 적분에 대해 2,877건 비교하여
모두 일치했습니다.

이 구조의 핵심은 **물리 계층이 화면에서 분리되었다는 점**입니다. 계획서 7.1절이 요구하는
"웹 계산과 독립적인 Python 계산 또는 수기 계산의 비교"를 이제 브라우저를 열지 않고
Node에서 바로 수행할 수 있습니다.

## 2. 다음에 할 작업 (우선순위 순)

### 2.1 단계 0을 실제로 닫기 — 장치 실측값과 센서 좌표

계획서가 "가장 먼저 확보할 자료"로 지목한 항목이며, 지금 코드에서 가장 큰 불확실성입니다.
`physics/constants.js` 한 파일만 고치면 전체 계산이 따라 바뀌도록 구성해 두었으므로,
실측값이 들어오는 순간 반영 비용은 거의 없습니다.

- duct, 실린더, 가열 벽의 치수
- T5·T6·T7·T8·T10의 실제 좌표 (CFD probe 위치와 같은 좌표계로 정의)
- 가열 시작부터 정상상태까지의 온도 시간 기록 한 세트 이상

센서 좌표는 `data/components.js`에도 좌표 항목으로 함께 넣어, 장치 도식과 CFD 화면이
같은 좌표 정의를 공유하도록 합니다.

### 2.2 검증 체계 — 1차 완료, 남은 항목 있음

검증은 저장소에 상주하는 두 층으로 구성했습니다.

| 명령 | 무엇을 보는가 | 규모 |
|---|---|---|
| `npm test` | 모델이 지켜야 할 성질 (부호, 단조성, 열수지, 수렴) | 25개 |
| `npm run verify` | scipy 독립 구현과의 교차 비교 | 2,168건 |

교차 검증은 **일부러 다른 알고리즘**을 씁니다. 웹은 이분법과 고정 간격 RK4로 풀고,
파이썬은 Brent 법과 적응형 Runge-Kutta로 풉니다. 복사도 웹은 선형화한 계수로,
파이썬은 T⁴ 차이로 직접 계산합니다. 같은 방법을 두 번 구현하면 같은 실수를 두 번
하므로 검증이 되지 않기 때문입니다. 환경은 `uv`가 관리하므로 설치 절차가 없습니다.

이 체계가 곧바로 결함 하나를 찾았습니다. `simulateCylinder`에서 적분 간격이 계산
시간을 정확히 나누지 못하면 마지막 점의 라벨과 실제 적분 시각이 어긋났습니다.
UI의 기본 입력이 30초 단위라 드러나지 않았지만, 값을 직접 입력하면 나타났습니다.

계획서 7.1절 중 아직 다루지 못한 항목은 다음과 같습니다.

- 단위 변환 검사의 자동화 — `pint`를 도입하면 °C와 K, mm와 m을 섞었을 때 예외가 납니다
- 한 조건에서 보정한 파라미터를 다른 조건에서 확인 — 실측 시간 기록이 있어야 가능합니다
- 조교가 브라우저에서 열어 확인하는 검증 페이지 — 설치 없이 돌아가야 몇 년 뒤에도 씁니다

### 2.3 결과 출처 배지를 데이터로 관리

계획서 5.8절은 모든 결과에 `측정값`, `교안 기반 계산`, `사용자 가정` 같은 배지를 붙이도록
요구합니다. 현재는 배지 문구가 마크업에 직접 적혀 있어서, 계산 방식이 바뀌어도 배지는
그대로 남습니다. 각 출력 항목과 그 근거를 짝지은 `data/provenance.js`를 만들고 화면이
그 값을 읽어 배지를 렌더링하면, 배지와 실제 계산 방식이 어긋나지 않습니다.

같은 맥락에서 `모델과 가정`은 현재 다이얼로그 하나에 들어 있습니다. 계획서가 이 기능의
교육 효과를 `매우 높음`으로 두고 있고, case별 경계조건과 압축 오차까지 표로 보여야 하므로,
독립된 화면으로 올리는 편이 적절합니다.

### 2.4 CFD case 파일 형식을 계산 전에 확정

이 결정은 웹보다 CFD 후처리 스크립트를 더 크게 구속합니다. 계산을 다 마친 뒤에
형식을 정하면 후처리를 다시 돌려야 하므로, 단계 3에 들어가기 전에 고정해야 합니다.

제안하는 구성은 case 하나당 세 파일입니다.

```text
data/cfd/<caseId>/
  manifest.json    경계조건, 격자 해상도, 양자화 방식과 오차, 복사 처리 방식, solver 버전
  field.bin        Int16으로 양자화한 온도·속도 단면 (manifest의 min/max로 복원)
  surface.json     표면 위치별 대류·복사 열유속과, 원본 격자에서 적분한 총 열전달량
```

총 열전달량을 `surface.json`에 따로 저장하는 이유는 계획서 5.6절의 요구 때문입니다.
표시용으로 축소한 격자에서 다시 적분하면 값이 달라지므로, 원본에서 계산한 값을 함께
배포하고 화면은 그 값을 그대로 표시해야 합니다.

웹 쪽 작업은 `data/synthetic-field.js`를 같은 인터페이스(`fieldSample`, `palette`)를 가진
`data/cfd-loader.js`로 교체하는 것으로 끝납니다. 이번 분리 작업에서 합성 필드를
별도 모듈로 떼어 둔 이유가 여기에 있습니다.

### 2.5 유동장 재생 중의 불필요한 다시 그리기

현재 재생 버튼을 누르면 매 프레임마다 필드 이미지뿐 아니라 비교 그래프와 요약 표까지
다시 계산합니다(`drawField` → `updateCfdSummary` → `drawCfdComparison`). 이번 분리에서는
동작을 바꾸지 않기 위해 그대로 두었습니다. 요약 갱신 주기를 프레임에서 떼어내면
저사양 노트북에서의 재생이 눈에 띄게 가벼워집니다. 계획서 7.6절의 사용성 검증 항목과
직접 연결됩니다.

### 2.6 학생 데이터 저장과 CSV 불러오기

현재는 표 입력과 CSV 내보내기만 있습니다. 계획서 단계 2가 요구하는 CSV 불러오기,
입력값 검증, 브라우저 내부 임시 저장이 아직 없습니다. `localStorage`에 저장하되,
저장 시점과 저장 위치를 화면에 명시하여 "외부 서버로 전송하지 않는다"는 운영 원칙이
학생에게 보이도록 합니다.

## 3. 배포 방식 검토

### 3.1 정적 호스팅이라는 선택 자체는 타당합니다

계산 서버 없이 브라우저에서만 계산하고, CFD는 미리 계산한 결과를 읽기만 하는 구조는
정적 호스팅과 정확히 맞습니다. 학생 계정과 데이터베이스를 두지 않기로 한 결정 덕분에
운영 비용과 개인정보 처리 부담이 모두 사라집니다. 이 방향은 유지하는 것이 좋습니다.

### 3.2 GitHub Pages의 적합성

현재 저장소 그대로 GitHub Pages를 켜면 됩니다. 이번에 `index.html`을 저장소 최상위에
만들고 `.nojekyll`을 추가했으므로, `Settings → Pages`에서 `main` 브랜치의 `/ (root)`를
지정하는 것으로 배포가 시작됩니다. 자산 경로를 모두 상대 경로로 두었기 때문에
`https://<계정>.github.io/CBPrcsLab-HeatTransfer/` 같은 하위 경로에서도 그대로 동작합니다.

**단계 1~2에서는 GitHub Pages로 충분합니다.** 무료이고, HTTPS가 자동으로 적용되며,
빌드 도구가 필요 없는 현재 구조와 잘 맞습니다.

다만 CFD 데이터가 들어오는 단계 3 이후에는 다음 세 가지가 제약으로 나타납니다.

**첫째, 응답 헤더를 지정할 수 없습니다.** GitHub Pages는 캐시 수명을 짧게 고정해 두기
때문에, 수 MB짜리 case 파일을 학생이 화면을 옮길 때마다 다시 내려받게 될 수 있습니다.
Cloudflare Pages나 Netlify는 `_headers` 파일로 `Cache-Control: immutable`을 지정할 수
있어서, 파일명에 버전을 넣어 두면 한 번 받은 case를 다시 받지 않습니다.

**둘째, 이진 데이터의 압축이 적용되지 않습니다.** GitHub Pages는 텍스트 계열에는 gzip을
적용하지만 `application/octet-stream`에는 적용하지 않습니다. 계획서 5.6절이 요구하는
gzip/Brotli 압축 효과를 얻으려면 미리 압축한 `.bin.gz`를 올리고 브라우저에서
`DecompressionStream("gzip")`으로 풀어야 합니다. 이 방식은 GitHub Pages에서도 잘 동작하므로
호스팅을 바꾸지 않고도 해결할 수 있습니다.

**셋째, git 이력에 이진 파일이 누적됩니다.** CFD 결과를 몇 차례 다시 계산해 교체하면
과거 버전이 모두 저장소에 남아 clone이 무거워집니다. 정상상태 2D 단면 10개 정도라면
전체가 수십 MB 수준이므로 문제가 되지 않지만, 단계 5의 transient frame이 들어오면
빠르게 커집니다. 이때는 데이터를 별도 저장소나 GitHub Releases로 분리하는 편이 낫습니다.

### 3.3 대안 비교

| 항목 | GitHub Pages | Cloudflare Pages | Netlify |
|---|---|---|---|
| 비용 | 무료 | 무료 | 무료 (대역폭 100 GB/월) |
| 응답 헤더 지정 | 불가 | `_headers` 지원 | `_headers` 지원 |
| 비공개 저장소 | 유료 플랜 필요 | 무료 플랜에서 가능 | 무료 플랜에서 가능 |
| 대역폭 | 월 100 GB 권고치 | 사실상 무제한 | 월 100 GB |
| 저장소 연동 | 기본 제공 | GitHub 연동 | GitHub 연동 |
| 설정 부담 | 가장 낮음 | 낮음 | 낮음 |

### 3.4 권고

**단계 2까지는 GitHub Pages를 그대로 사용하고, 아래 조건 중 하나가 발생하면 Cloudflare
Pages로 옮기는 것을 권합니다.**

- CFD case 파일의 반복 다운로드가 실제로 느리게 느껴질 때 (캐시 헤더가 필요한 시점)
- 도구를 수업 참여자에게만 공개해야 해서 저장소를 비공개로 돌려야 할 때
- 웹에 배포하는 데이터 총량이 100 MB를 넘어설 때

옮기는 비용은 크지 않습니다. 빌드 과정이 없는 정적 사이트이므로 저장소를 연결하고
출력 디렉터리를 지정하면 끝나며, 코드는 손대지 않아도 됩니다. 지금 결정을 서두를 필요는
없고, 단계 3의 CFD 데이터 크기가 확정된 뒤에 판단하면 됩니다.

### 3.5 지금 함께 정리하면 좋은 운영 습관

현재 저장소의 커밋은 모두 GitHub 웹 화면에서 올린 `Add files via upload`입니다.
파일이 여러 개로 나뉜 지금부터는 로컬에서 작업하고 커밋 단위를 의미별로 나누는 편이,
어떤 변경이 계산 결과를 바꾸었는지 나중에 추적하기 쉽습니다. 특히 `physics/`의 수정은
계산 결과를 직접 바꾸므로, 검증 스크립트 결과와 함께 커밋하는 습관이 도움이 됩니다.

또한 학생에게 이미 `heat_transfer_ui_prototype.html` 주소를 공유한 적이 있다면,
같은 이름으로 `index.html`로 보내는 한 줄짜리 리다이렉트 파일을 두어 기존 링크가
끊기지 않게 할 수 있습니다.
